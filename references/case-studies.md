# 사례와 해석

개발 주체의 공개 문서와 연구를 읽어 도출한 분석이다. 해당 서버를 직접 배포하거나 공격·벤치마크를 재현한 결과가 아니다. 저장소 문서는 특정 커밋 전 코드 감사와 구별한다.

## GitHub MCP Server [R18]

관찰: 도구 집합·개별 도구 선택과 읽기 전용 모드를 문서화한다. Lockdown은 최선 노력 콘텐츠 필터이고 인가 경계가 아니라고 명시한다.

설계 추론: 도구 노출 축소, 콘텐츠 필터, 실제 호출의 객체 인가는 별개 통제로 둔다. 직접 호출 우회와 기존 자격증명의 실제 권한을 시험한다. C05/C06 → T11/T12/T15.

## Spotify Honk [R19, R20]

관찰: 제한된 도구와 검증 추상화, 완료 경로의 검증 작업을 설명한다.

설계 추론: 모델의 완료 주장에 의존하지 말고 실행기·CI에서 검사한다. 모델 판단은 결정론적 테스트를 대신하지 않는다. C06/C09/C14 → T15/T22/T34/T35.

## Spotify Ads [R21]

관찰: 특정 연동에 CLI·OpenAPI·스킬을 선택하며 도구 문맥·유지보수 부담을 비교했다.

설계 추론: ‘왜 MCP인가’를 초기 결정으로 둔다. MCP나 CLI의 우월성을 일반화하지 않고 실제 호스트·과제·보안 경계로 평가한다. C01/C06 → T01/T15.

## Cloudflare [R22]

관찰: OAuth 및 기존 SSO 제공자 연결 예시가 있다.

설계 추론: 검증된 인증 어댑터를 재사용하되 로그인 성공과 객체별 인가를 구분한다. 특정 벤더를 보편 필수로 두지 않는다. C04/C05/C07 → T08–T12/T16.

## Anthropic 도구 설계 [R23]

관찰: 작업 중심 도구·명확한 결과와 실제 과제 기반 평가를 제시한다.

설계 추론: 스키마 적합성과 모델의 과제 성공을 별도 평가한다. 도구 설명·스키마 변경에 회귀 평가를 연결한다. C06/C14 → T13–T15/T34.

## Invariant Labs의 통제된 GitHub 시연 [R24]

관찰: 공개 이슈의 간접 지시가 비공개 정보 읽기와 공개 쓰기로 이어지는 경로를 시연했다.

설계 추론: 사용자 권한뿐 아니라 데이터의 출처·반출 목적지를 통제한다. 실제 피해 사건이나 현재 제품 전체의 미해결 결함으로 표현하지 않는다. C08 → T18/T19.

## MCPTox / MCP-Bench / MCP-SafetyBench [R25–R27]

관찰: 각각 악성 도구 메타데이터, 복합 업무 수행, 복수 계층·턴·서버 조합 안전성을 평가한다.

설계 추론: metadata/result/direct-user 입력을 분리하고, schema/trajectory/task outcome과 정책 위반을 함께 측정한다. 과거 특정 모델의 공격 성공률을 현재 환경에 그대로 적용하지 않는다. C08/C14 → T18/T19/T34.

## 공식 Reference Servers와 Conformance [R28, R29]

관찰: 참고 서버는 교육용 예시임을 명시한다. 적합성 도구는 requirement set과 기대 실패·제외를 구분한다.

설계 추론: 복사 가능한 예시는 운영 준비 증거가 아니고 exit 0은 전체 시험 통과가 아니다. C02/C14/C15 → T02/T33/T35.
